
### A. Artifacts Management (`actions/upload-artifact` & `download-artifact`)
* **Concept:** Persisting build files (logs, compiled code, binaries) produced by one job to share with subsequent jobs or download from the GitHub UI.
* **Why Use It:** Each GitHub Actions job executes on an isolated, clean virtual machine. Once a job finishes, its environment is destroyed. Artifacts allow file transfer between isolated jobs.

### B. Conditional Execution (`if:`)
* **Concept:** Executing steps or jobs only when specific conditions evaluate to `true`.
* **Why Use It:** Restricts deployment to production branches (e.g., `main`), sends alerts on failures, or skips unnecessary steps.

## 1. Complete Hands-on YAML Configurations

### Workflow 1 : Artifacts & Conditional Pipeline (artifacts-pipeline.yml)

```
name: Artifacts and Conditional Pipeline

on:
  push:
    branches:
      - main
  workflow_dispatch:

jobs:
  build-job:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Generate Build Output
        run: |
          mkdir build_output
          echo "Build Artifact Version 1.0 - Generated by ${{ github.actor }}" > build_output/app-v1.txt

      - name: Upload Build Artifact
        uses: actions/upload-artifact@v4
        with:
          name: web-app-build
          path: build_output/app-v1.txt

  deploy-job:
    needs: build-job
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Download Build Artifact
        uses: actions/download-artifact@v4
        with:
          name: web-app-build

      - name: Verify Downloaded File
        run: |
          echo "Reading downloaded artifact content:"
          cat app-v1.txt
```

#### Interview Questions & Answers

***Q1:*** Why do we need actions/checkout@v4 in almost every workflow?
***Answer:*** GitHub Actions runners are clean, isolated virtual environments with no access to repository source code by default. actions/checkout@v4 clones the repositor code into the runner workspace so subsequent steps can process it.

***Q2:*** How does strategy.matrix save time in CI/CD pipelines?
***Answer:*** It automates multi-environment testing by spinning up parallel runners for all specified parameter combinations (e.g., OS types, runtime versions) from a single YAML configuration block.

***Q3:*** Why can't deploy-job directly access files created in build-job without Artifacts?

***Answer:*** Every job in GitHub Actions executes on its own fresh virtual machine runner. Once a job completes, its runner environment is discarded. Artifact actions (upload-artifact and download-artifact) store build outputs centrally to pass them across independent job environments.

***Q4:*** How do you restrict a deployment job to run only on the main branch?

***Answer:*** By adding a conditional statement at the job level using if: github.ref == 'refs/heads/main'.
